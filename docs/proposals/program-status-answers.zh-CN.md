# 扩展提案：在终端里直接回答等待中的程序（OSC 7501）

*[English](program-status-answers.md) | 简体中文*

状态：草案，供 [Program Status Protocol][spec] 的维护者以及 Claude Code、Codex 的维护者讨论。它是对规范修订版 0.4 的扩展；是否以及如何纳入某个修订版，由规范维护者决定。以下内容尚未实现；XaYa 目前实现的是修订版 0.4（只有状态上报）。

[spec]: https://www.superlogical.com/rex/docs/build/program-status

## 问题

有了 Program Status Protocol，终端能知道 agent 什么时候在等用户，以及在等什么（`kind=permission|question|auth`，问题内容放在 `msg` 里）。XaYa 用这些信息显示标题徽标、Dock 计数、桌面通知，以及一个列出所有窗口的 agent 面板。

但要回答，用户仍然得找到那个窗口、切过去，再按 agent 界面要求的键。同时跑好几个 agent 时，大部分打断都是例行的批准，用户本可以在通知或面板里直接给出，不必切换上下文。

终端今天做不到这一点，除非去猜 agent 的界面：往全屏 TUI 里敲 `y` 或回车，结果取决于它当时的布局和焦点，猜错就会批准错误的操作。批准是安全边界，所以需要明确的协议，而不是模拟按键。

## 概览

1. 终端声明自己能发送回答。
2. 处于等待状态的程序可以给出**选项**，并附上一个**请求 id**。
3. 用户在终端的界面里选中一项后，终端把**回答**写入程序的输入。
4. 程序把它当作用户在自己界面里按了对应的键来处理，或者忽略它，然后照常上报新状态。

不实现本提案的程序和终端，仍按修订版 0.4 工作。

## 与现有安全模型的关系

修订版 0.4 承诺：终端唯一会写回的字节是能力探测的回复，其中不含任何上报的内容；id、标题和消息永远不会被送回。这保证了程序无法借助终端获取任何信息，终端也不会替程序做任何事。

本扩展有意增加了第二种写回内容，因此必须守住这两点：

- **除程序自己为此给出的内容外，上报中的任何东西都不会流回。** 回答只包含请求 id 和程序自己提供的、来自固定词汇表的选项 id。标题、消息和标签永不回显，也无法读取其他记录。
- **终端从不自行回答。** 回答只发生在用户于终端界面中直接操作之后；程序无法让终端回答，其他程序也不能，除非用户主动开启。
- **回答能做的，不超过在程序里按一次键。** 程序会把请求 id 与当前显示的提示比对，并完全按自己界面的方式应用选项，所以过期、重放或伪造的回答都不起作用。
- **双方都需主动开启。** 终端没有声明 `answers=1`、或程序没有给出 `req`/`choices` 时，一切照旧：所有不使用本扩展的会话，0.4 的保证依然成立。

## 传输格式

语法沿用修订版 0.4：`OSC 7501 ; key=value:key=value… ST`，值限定为 `[A-Za-z0-9_.,+/=-]`，自由文本用 base64 编码。

### 能力声明

终端对 `OSC 7501 ; ?` 的回复增加 `answers` 能力：

```
OSC 7501 ; ? : states=idle,working,done,blocked,error : kinds=permission,question,auth : answers=1 ST
```

程序只向声明了 `answers=1` 的终端提供选项。

### 提供选项

`blocked` 上报可以带上：

| 键        | 值                                                    |
|-----------|-------------------------------------------------------|
| `req`     | 请求 id，`[A-Za-z0-9_.-]{1,32}`，每个等待中的提示唯一 |
| `choices` | 逗号分隔的选项 id，最多 9 个                          |
| `labels`  | 可选；各选项标签的 base64，按顺序以换行分隔           |

对 `kind=permission`，选项 id 为 `allow`、`deny` 和 `always`（允许并记住）；对 `kind=question`，为 `opt1` … `opt9`，顺序与程序显示的一致。自由文本回答不在本提案范围内，它需要程序自己的输入框。

```
OSC 7501 ; state=blocked : app=claude-code : kind=permission : req=p42 :
  choices=allow,always,deny : labels=<base64 "Yes\nYes, don't ask again\nNo"> :
  msg=<base64 "Run: cargo test --workspace"> ST
```

### 回答

终端把回答写入程序的输入，方式与它回复其他查询相同：

```
OSC 7501 ; answer=p42 : choice=allow ST
```

程序从输入流中读取它，就像它已经在解析的 DA1 或 OSC 11 回复一样。

## 规则

对程序：

- 只有当 `answer` 指向当前正在显示的请求、且 `choice` 是为它提供过的选项时，才接受回答；其他一律静默丢弃。过期、重放或伪造的回答不起任何作用。
- 应用回答的效果必须与在程序自身界面里按对应键完全相同，不多做任何事。
- 应用之后，上报新状态（`working`，或带新 `req` 的 `blocked`）。终端依据的是这个上报，而不是“已经发出了回答”。
- 对于程序认为过于敏感的提示（例如 `kind=auth`），可以不提供选项。

对终端：

- 只在用户于终端自身界面中直接操作时发送回答，例如点击通知按钮、在 agent 面板里按键。来自其他程序的回答（例如通过终端的 IPC）必须默认关闭。
- 在用户选择的选项旁边，原样显示程序的 `msg` 和 `labels`，并去掉双向文本控制字符（修订版 0.4 已有此要求）。
- 不为程序已不再显示的请求发送回答：程序之后的任何一次上报，都会使先前提供的选项失效。

## XaYa 会怎么做

- `kind=permission` 的桌面通知会把提供的选项显示为按钮（macOS 通知操作）。
- agent 面板显示所选窗口的选项；按数字键回答，回答前面板会先显示将要回答的内容。
- `xaya msg answer -w <window> <choice>`，与 `msg send-text` 一样，默认关闭，需要在配置中开启。

## 待讨论的问题

- 程序是否应该能要求：只有在它的窗口对用户可见时才接受回答？
- `always` 值得放进共用词汇表吗？还是持久授权应该留给程序自己的界面？
- 程序是否应该显式确认回答（`answered=p42`），而不是通过下一次上报来体现？
